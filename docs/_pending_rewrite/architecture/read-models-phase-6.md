# Read Model Architecture (Phase 6)

## Overview
This document defines the governed read models introduced in Phase 6 to address performance bottlenecks identified in the legacy "Live Computed" reporting logic.

## Classification of Expensive Reads

| Operation | Current Implementation | Performance Risk | Classification |
| :--- | :--- | :--- | :--- |
| **Inventory Summary** | Python-side loop over `InventoryTxn` (signals) and `Batch` (availability). | O(N items * Txns) - CPU bound app side. | Live Computed |
| **Ledger Health** | Iterates ALL batches, calls `calculate_ledger_balance` (sum txn) for each. | O(Batches * Txns) - Database IO explosion. | Live Computed (Critical) |
| **Item Signals** | Ad-hoc aggregation of `InventoryTxn` for single item. | Moderate, but redundant with summary. | Live Computed |

## Proposed Explicit Read Models

### 1. `batch_ledger_balance_view`
**Purpose**: Provide the authoritative "Ledger Truth" quantity for every batch without calculating it row-by-row in Python.
**Source**: `inventory_txn`
**Logic**: 
```sql
SELECT batch_id, SUM(base_qty) as ledger_qty 
FROM inventory_txn 
WHERE status = 'COMMITTED' 
GROUP BY batch_id
```
**Freshness**: Real-time (Standard View).

### 2. `inventory_signal_view`
**Purpose**: Pre-calculate outflow signals (Last 7 Days, Prev 7 Days) for all items.
**Source**: `inventory_txn`
**Logic**: Windowed sums of `base_qty` for `txn_type = 'OUT'`.
**Freshness**: Real-time (Standard View).

## Governance Rules
1.  **Truth Source**: These views MUST derive directly from `inventory_txn` (the Ledger).
2.  **No Business Logic**: Views only aggregate; they do not interpret "Healthy" vs "Critical". That logic remains in the Service Layer (specifically `reconciliation.py`).
3.  **No Mutation**: These are read-only interfaces.

## Caching Strategy (Optional Phase)
If views are insufficient, we may introduce `@cache` with TTL, but only for `get_inventory_report`. `get_ledger_health_report` MUST remain fresh or strictly explicitly versioned.
