# Phase R4 — Rejections Pagination & Performance Hardening

## Goal
Eliminate unbounded reads in the Rejections system and ensure safe scaling by implementing pagination and query optimizations.

## 1. Backend Design

### API Changes
**Endpoint**: `GET /rejection-entries/list` (and potentially root `/` if used for list)
**Parameters**:
- `skip` (int, default: 0)
- `limit` (int, default: 50, max: 100)
- Existing filters (`rejection_date`, `item_ids`)

**Response Schema**:
```json
{
  "items": [ ... ],
  "skip": 0,
  "limit": 50,
  "total": 120,
  "has_more": true
}
```

### Query Optimization
- **Eager Loading**: Use `joinedload` for `RejectionEntry.batch` and `RejectionEntry.item` to prevent N+1 queries during serialization.
- **Indexing**: Ensure `created_at`, `item_id`, and `is_active` are indexed (if not already handled by DB setup or previous phases). *Note: Phase D1/R2 might have established some, but explicitly checking/adding via alembic if needed.*

### Pagination Logic
- `total` count query applied with filters.
- `items` query with `offset(skip).limit(limit)`.
- `has_more` calculation: `(skip + len(items)) < total`.

## 2. Frontend Design

### UX Strategy
- **Pattern**: "Load More" button (Explicit Paging).
- **Rationale**: Operational clarity. Infinite scroll can hide footer info/actions and trigger accidental loads in a data-heavy tool. Explicit action confirms user intent to dig deeper.

### State Management
- `_skip`: Current offset.
- `_limit`: Page size (match backend default).
- `_total`: Total records available.
- `_rejections`: List<Map> (Cumulative).
- **Reset Trigger**: Changing Date or Item filter *must* reset `_skip = 0` and clear `_rejections`.

## 3. Backward Compatibility
- The frontend currently expects `List<RejectionEntryRead>`.
- **Breaking Change Management**:
